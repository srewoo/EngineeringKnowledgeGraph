3. In CallAI, both meetings and persons are marked as internal and external.
   How does that work? What if I just change some historical persons from
   internal to external, what would be the behaviour of the system?
================================================================================

PERSONS — types stored in `person-service`:

  data/repos/person-service/src/constant.py:25-29
    class PersonType(Enum):
        TEAM     = 0   # internal employee
        UNKNOWN  = 1
        PROSPECT = 2   # external party

  Updates: src/workflows/person_update.py and src/utils/person_utils.py
  (`async def update_person(... typee: Union[PersonType, None] ...)`).

MEETINGS — `external_type` is computed at notification time from participant
list, NOT stored as a persistent column on the meeting:

  data/repos/meeting-objects/src/meeting_utils/notification_utils/notifier.py:213
    async def determine_external_participant(pid_uid_dict, domain_emails,
                                              person_loader) -> bool:
  …meeting is "external" if any participant's PersonType is PROSPECT or UNKNOWN.

  data/repos/meeting-objects/src/utils/notification_utils.py:179, 204
    "Participants are ordered as [<external>, <unknown>, <internal>]"

BEHAVIOUR IF YOU FLIP HISTORICAL PERSONS FROM TEAM → PROSPECT:

  Direct effects:
  - Future calls of `determine_external_participant` for any meeting that
    contains those persons will start returning True. From that point:
    - Notification messages flip to the external-participant template
      (notification_utils.py:268-276 — uses `LinkShareComponentUrl.EXTERNAL`).
    - Share links generated via `get_share_redirect_link(... external_type
      = True ...)` route through external-share components.
  - `meeting_utils/notification_utils/message_builder.py:60` — those persons
    move into `external_participants` in templated emails:
        external_participants = participant.get(PROSPECT, []) +
                                participant.get(UNKNOWN, [])

  Side effects to expect:
  - External-share permission gates (`external_call_share_enable` tenant
    flag in `callai-help-scripts/src/routes/tenant_create.py:85`) start
    applying retroactively.
  - Any analytics view filtering on participant type
    (`external_share_v4_{tenant_id}` materialised view —
    `callai-help-scripts/update_views_sql.py:126`) reclassifies historical
    rows on next refresh.
  - Email-digest jobs scoped to "external shared meetings"
    (callai-help-scripts/src/rep_email_digest/queries.py:128 —
     `get_external_shared_activity`) start surfacing those meetings to reps.

  No direct effect on the meeting record itself (no schema migration), since
  internal/external for meetings is derived, not stored.

  data/repos/person-service/src/workflows/person_create.py:11

  data/repos/person-service/src/workflows/person_update.py:15

  data/repos/person-service/src/workflows/person_merge.py:44-45

So persons can be flipped between TEAM/PROSPECT/UNKNOWN at any time via
person-service APIs, and that change drives meeting-level classification
on the next read.
